# HEX 文本与原始二进制数据

## 本文解决什么问题

日志里看到 `41 42`，它可能是两个原始字节的显示，也可能是五个 ASCII 字符。抓包工具里的 `0A`、C 代码里的 `"0A"` 和 `0x0A` 也不是同一份数据。本文建立“数值—字节—文本表示”之间的转换边界。

## 阅读前需要知道什么

- [整数、进制与位模式](./integer-radix-bit-pattern)中的进制只是数值写法。
- [字节、字符、编码与字符串](./bytes-characters-encoding)中的文本必须通过编码才能变成字节。

## 三种容易混淆的对象

| 写法或显示 | 实际对象 | 若存储，典型 byte 数 |
| --- | --- | ---: |
| 数值 `0x41` | 整数 65 的十六进制写法 | 取决于类型 |
| 字节数组 `{0x41, 0x42}` | 两个原始 byte | 2 |
| 文本 `"41 42"` | 字符 `4 1 空格 4 2` | ASCII/UTF-8 下为 5 |

HEX（hexadecimal）不是一种字符编码，也不是独立的数据类型。它只是用 `0`～`9`、`A`～`F` 表示数值的方式。每个 byte 需要两个十六进制数字，因为一个十六进制位承载 4 bit。

```text
原始 byte:  0100 0001  0100 0010
HEX 显示:      4    1      4    2
```

显示时加入的空格、冒号和 `0x` 前缀通常只是给人看的分隔符，并未出现在原始数据中。

## 同一个“41 42”怎样占用不同空间

假设文件中真实保存了两个 byte `0x41 0x42`，文件大小就是 2 byte，文本查看器通常显示 `AB`。

如果文件中保存的是字符序列 `41 42`，ASCII 或 UTF-8 编码后是：

```text
字符:    '4'  '1'  ' '  '4'  '2'
字节:     34   31   20   34   32
```

文件大小为 5 byte。把这个文本“按 HEX 解析”才会得到 `41 42` 两个 byte；仅仅复制文本并没有完成解析。

## C 代码中的四种写法

```c
uint8_t a = 0x41;                    /* 一个整数对象，值为 65。 */
uint8_t b[] = {0x41, 0x42};          /* 两个原始 byte。 */
char c[] = "41 42";                 /* 5 个文本 byte + 结尾 NUL。 */
char d[] = "\x41\x42";             /* 两个字符 byte + 结尾 NUL。 */
```

`\x41` 是 C 源代码中的十六进制转义，编译后并不保留反斜杠和 `x`。但 C 的 `\x` 会继续吞入后续所有十六进制数字，`"\x41B"` 可能不是想象中的 `A`、`B`；工程上可分开写成 `"\x41" "B"`，并让编译器在相邻字符串字面量阶段连接。

## 解析 HEX 文本的明确规则

一个可靠解析器需要先声明语法，而不是“尽量猜”：

1. 是否允许连续形式 `4142`。
2. 允许哪些分隔符，例如空格、逗号、冒号。
3. 是否允许每组出现 `0x` 前缀。
4. 奇数个 HEX 数字是报错还是补零。
5. 最大输入长度是多少。

本站工具选择严格模式：允许常见分隔符与可选 `0x`，但不接受未知字符，也不把 `ABC` 自动改成 `0A BC` 或 `AB C0`。静默补零会改变帧边界，调试协议时风险很大。

## HEX dump 应该同时提供什么

常见十六进制转储（hex dump）会同时显示偏移、HEX 字节和可打印 ASCII：

```text
0000  45 6D 62 65 64 00 FF 0A  |Embed...|
```

- `0000` 是这一行首字节相对数据起点的偏移。
- 中间才是原始 byte 的 HEX 表示。
- 右侧 ASCII 预览只是辅助；不可打印或非 ASCII byte 通常显示为 `.`。

ASCII 预览不能用来判断 UTF-8 是否正确，因为一个中文字符的每个组成 byte 都超出 ASCII 可打印范围。需要先按完整编码序列解码。

## 字节序不改变 HEX 数字内部顺序

字节序（endianness）只讨论多字节数值中，各个 byte 的排列。例如整数 `0x1234`：

```text
大端字节序：12 34
小端字节序：34 12
```

不会把一个 byte `0x12` 写成 `0x21`。后者是半字节（nibble）顺序变化，属于另一个问题。也不要把 SPI/I²C 线路上的位发送顺序直接称为 CPU 字节序。

## 常见错误与排查

| 现象 | 常见原因 | 检查方法 |
| --- | --- | --- |
| 发送 `41 42`，对端收到 `34 31 20 34 32` | 发送了 HEX 文本而非解析后的字节 | 在发送 API 前打印缓冲区长度与实际 byte |
| `0A` 被当成两个字符 | 输入框或串口工具处于文本模式 | 切换 HEX 模式并确认模式含义 |
| 奇数位输入结果与预期不同 | 工具自动在左侧或右侧补零 | 使用严格解析器并明确报错 |
| 中文在 ASCII 预览中全是点 | 逐 byte 预览不是 UTF-8 解码 | 使用严格 UTF-8 解码完整序列 |
| 多字节字段数值反了 | 字节序与协议规定不一致 | 按字段边界标注 byte，再组合数值 |

## 工程建议

- 日志标明 `TX HEX:`、`RX HEX:`，不要只输出一串无上下文数字。
- 协议文档同时给出字段值、byte 数和线上字节序列。
- 保存原始抓包文件；HEX 文本适合阅读，但体积更大且可能混入格式字符。
- 测试中比较 byte 数组，不要只比较格式化后的字符串。
- 明确“文本输入模式”和“HEX 输入模式”，不要自动猜测。
