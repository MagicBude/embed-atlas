# C 定宽整数、整数提升与溢出边界

`uint8_t` 对象占 8 bit，并不代表包含它的整个表达式都以 8 bit 运算。`0xFF` 看起来像一个字节，也不代表该整数字面量的类型就是 `uint8_t`。C 会在运算前进行整数提升和类型转换，运算后才可能缩窄回目标对象。

本文把前三篇文章中的固定位宽数学模型连接到真实 C 表达式，重点解释“对象类型”“表达式类型”和“保存后的位模式”为何必须分开看。

## 本文解决什么问题

读完本文，你应该能够：

- 区分 `intN_t`、`uintN_t`、`int_leastN_t` 和 `int_fastN_t` 的用途。
- 解释为什么两个 `uint8_t` 相加时通常先变成 `int`。
- 判断有符号与无符号混合运算会转换到什么共同类型。
- 区分无符号模运算、有符号溢出和缩窄转换。
- 为整数字面量选择合适的 `UINT32_C`、`INT64_C` 或后缀。
- 避免移位、格式化输出和边界检查中的常见错误。

## 先分清对象、表达式和赋值

观察：

```c
uint8_t a = 200;
uint8_t b = 100;
uint8_t result = a + b;
```

这里至少有三个层次：

1. `a` 和 `b` 是 `uint8_t` 对象。
2. 表达式 `a + b` 会先进行整数提升；在常见 32 位 `int` 平台上，两者都提升为 `int`，数学结果是 `300`。
3. 把 `300` 转换并保存到 `uint8_t result` 时，结果才缩窄为 `44`，即 `300 modulo 256`。

所以，“8 位加法得到 44”不是这段 C 表达式完整的执行过程。更准确的说法是：先以提升后的类型得到 `300`，再转换到 8 位无符号对象得到 `44`。

## `<stdint.h>` 提供哪几类整数

### 精确宽度类型

`intN_t` 和 `uintN_t` 表示恰好 N bit 且没有填充位的整数类型，例如：

```c
int8_t
uint16_t
int32_t
uint64_t
```

这些名称只有在实现提供相应类型时才定义，不能假设所有符合标准的 C 环境都具备每一种精确宽度类型。在常见 MCU 工具链中，8、16、32 位类型通常存在，但可移植库仍应尊重这个条件。

### 最小宽度类型

`int_leastN_t` 和 `uint_leastN_t` 至少能提供 N bit 的表示宽度，并选择满足要求的较小类型：

```c
uint_least16_t counter;
```

适合表达“至少需要这个范围”，不要求对象必须恰好占 N bit。

### 快速最小宽度类型

`int_fastN_t` 和 `uint_fastN_t` 至少提供 N bit，并由实现选择通常较快的类型。它可能比 N 更宽：

```c
uint_fast8_t index;
```

不要用 `sizeof(uint_fast8_t) == 1` 作为协议、文件或寄存器布局前提。

### 指针与最大宽度类型

- `intptr_t`、`uintptr_t`：实现能够用整数无损往返对象指针时提供。
- `intmax_t`、`uintmax_t`：能表示标准库规定范围内最宽的普通整数值。

协议字段应按协议宽度选择类型；数组索引和对象大小通常优先使用 `size_t`；指针只在确有标准定义的转换需求时使用 `uintptr_t`。

## 整数提升为什么会改变小类型

C 会对转换等级不高于 `int`/`unsigned int` 的整数类型执行整数提升（Integer Promotions）：

```text
如果 int 能表示原类型的全部值 → 转换为 int
否则                         → 转换为 unsigned int
```

在 `int` 为 32 bit 的常见平台上：

| 原类型 | 常见提升结果 | 原因 |
| --- | --- | --- |
| `uint8_t` | `int` | 0～255 全部能由 `int` 表示 |
| `int8_t` | `int` | -128～127 全部能由 `int` 表示 |
| `uint16_t` | `int` | 若 `int` 最大值至少为 65535 |
| `uint16_t` | `unsigned int` | 16 位 `int` 无法表示全部值时 |

这也是代码不能只凭 typedef 名称推断中间表达式位宽的原因。

### NOT 的典型惊讶

```c
uint8_t value = UINT8_C(0x0F);
uint8_t result = ~value;
```

在常见平台中：

1. `value` 先提升为 `int`。
2. `~value` 在 `int` 宽度执行，产生类似 `0xFFFFFFF0` 的补码结果。
3. 赋值到 `uint8_t` 时才保留低 8 位，得到 `0xF0`。

最终结果符合 8 位 NOT，但中间表达式不是 8 位。如果它参与比较、右移或函数调用，提升后的高位就可能影响结果。

## 通常算术转换怎样寻找共同类型

`+`、`-`、`*`、`/`、`%`、比较和多数二元位运算会在整数提升后执行通常算术转换（Usual Arithmetic Conversions）。

当两个整数类型不同，可按下面的简化顺序理解：

1. 同为有符号或同为无符号：较低等级转换到较高等级。
2. 一有符号、一无符号：先比较转换等级和可表示范围。
3. 如果有符号类型能表示无符号类型全部值，无符号操作数转换到该有符号类型。
4. 否则可能把有符号操作数转换到对应或更高等级的无符号类型。

### 负数与无符号数比较

```c
int32_t signed_value = -1;
uint32_t unsigned_value = 1;

if (signed_value < unsigned_value) {
    /* 在常见 32 位 int32_t/uint32_t 平台上通常不会进入。 */
}
```

当两种类型等级相同而无符号类型不能由有符号类型完整表示时，`-1` 会转换成 `uint32_t` 的最大值。比较实际变成一个很大的无符号数与 `1` 比较。

工程建议：比较前让两个操作数在业务含义和范围上使用相容类型，不要用一次随意强制转换掩盖负值可能存在的事实。

## 无符号运算按模范围工作

N bit 无符号类型的值范围为 `0`～`2ᴺ - 1`。其算术结果超出范围时，按 `2ᴺ` 取模：

```c
uint8_t value = UINT8_MAX;
value = (uint8_t)(value + 1U);  /* 保存后为 0 */
```

无符号回绕是语言定义的行为，但“定义良好”不等于“业务正确”。计数器、长度、内存大小和安全边界通常不应静默回绕。

```c
if (amount > UINT32_MAX - increment) {
    /* 加法会超出 uint32_t，先处理错误。 */
} else {
    amount += increment;
}
```

## 有符号溢出不是普通回绕

若有符号整数算术结果不能由结果类型表示，C 程序会进入未定义行为（Undefined Behavior，UB）范围。编译器可以利用“有效程序不会发生这种溢出”的前提优化代码。

```c
int32_t value = INT32_MAX;
value = value + 1;  /* 不要把它描述成必然得到 INT32_MIN。 */
```

硬件指令可能留下低 32 位，但 C 抽象机语义不保证程序可以依赖这个结果。需要回绕时使用明确的无符号类型；需要拒绝溢出时，在运算前检查或使用实现提供的已检查运算设施。

### 检查必须发生在危险运算之前

```c
if (b > 0 && a > INT32_MAX - b) {
    /* 正方向溢出。 */
} else if (b < 0 && a < INT32_MIN - b) {
    /* 负方向溢出。 */
} else {
    int32_t sum = a + b;
}
```

先计算 `sum` 再检查是否越界已经太晚，因为危险表达式本身可能触发未定义行为。

## 转换与算术溢出要分开

把不能表示的值转换到目标整数类型，与在该类型中执行溢出算术不是同一规则：

- 转换到无符号类型：按目标范围模数反复调整，结果定义明确。
- 转换到有符号类型且值不可表示：结果可能由实现定义，或引发实现定义的信号。
- 有符号算术结果不可表示：未定义行为。

因此，下面的代码需要分别分析“加法用什么类型执行”和“赋值怎样转换”：

```c
uint16_t destination = left + right;
```

## 整数字面量也有类型

字面量的进制、数值大小和后缀共同决定它的候选类型：

```c
1          /* 通常是 int */
1U         /* unsigned int */
1UL        /* unsigned long */
UINT32_C(1)
INT64_C(42)
```

### 构造掩码时明确无符号宽度

```c
#define STATUS_ERROR_Msk (UINT32_C(1) << 31)
```

这比 `1 << 31` 更能表达意图。若 32 位 `int` 无法表示结果，后者可能在有符号左移边界出错。

不要为了“看起来统一”给所有常量都加 `ULL`。常量类型过宽也可能改变通常算术转换、格式化输出和静态分析结果。按接口需要选择类型。

## 移位需要同时检查值和数量

对表达式 `left << right` 或 `left >> right`：

- 两个操作数先分别进行整数提升。
- `right` 不能为负，也必须小于提升后 `left` 类型的宽度。
- 无符号左移按类型宽度的模数保留结果。
- 有符号左移只有在规范条件满足并且结果可表示时才能安全使用。
- 负有符号数右移的具体规则需要结合所用 C 版本与实现核对。

对于位掩码、协议打包和寄存器操作，优先使用无符号操作数，并在动态移位前验证数量：

```c
bool bit_mask_u32(unsigned position, uint32_t *mask)
{
    if (mask == NULL || position >= 32U) {
        return false;
    }

    *mask = UINT32_C(1) << position;
    return true;
}
```

## 输入输出使用 `<inttypes.h>` 宏

`int32_t` 不保证一定是 `int` 的 typedef，`int64_t` 也不保证一定是 `long long`。可移植格式化应使用 `<inttypes.h>`：

```c
#include <inttypes.h>
#include <stdint.h>
#include <stdio.h>

void print_sample(uint32_t value, int64_t offset)
{
    printf("value=%" PRIu32 ", hex=0x%08" PRIX32 "\n", value, value);
    printf("offset=%" PRId64 "\n", offset);
}
```

使用错误的可变参数格式说明符不仅可能显示错误，还会让 `printf` 按错误类型读取参数，进入未定义行为范围。

## 编译器警告和断言是防线，不是证明

建议在受支持的工具链中启用高价值警告，例如符号转换、隐式缩窄和移位边界相关选项，并把新增警告当作需要解释的问题。

可以用静态断言记录项目依赖的实现条件：

```c
#include <limits.h>
#include <stdint.h>

_Static_assert(CHAR_BIT == 8, "本协议实现要求 8-bit byte");
_Static_assert(sizeof(uint32_t) * CHAR_BIT == 32, "需要精确 32-bit uint32_t");
```

断言能让不满足前提的平台快速失败，但不能代替对每个表达式的类型分析。

## 常见错误与排查

| 现象或说法 | 问题在哪里 | 正确检查方法 |
| --- | --- | --- |
| “`uint8_t + uint8_t` 一定是 8 位加法” | 忽略整数提升 | 用编译器类型信息或按 `int` 可表示范围推导 |
| “无符号回绕合法，所以长度溢出没关系” | 混淆语言定义与业务要求 | 运算前做上界检查 |
| “有符号溢出就是补码回绕” | 把硬件低位结果当成 C 语义 | 使用无符号模型或已检查运算 |
| “强制转换可以修复溢出” | 危险算术可能在转换前已经发生 | 先扩宽或先检查，再执行运算 |
| “`1 << 31` 就是 32 位最高位掩码” | `1` 通常是有符号 `int` | 使用 `UINT32_C(1) << 31` |
| “`uint_fast8_t` 一定占 1 byte” | fast 类型只保证最小宽度 | 用 `sizeof` 验证实现，布局使用精确协议类型 |
| “`%u` 可以打印所有无符号定宽类型” | typedef 的底层类型不固定 | 使用 `<inttypes.h>` 的 `PRI...` 宏 |
| “关闭警告就能保持旧代码行为” | 编译器优化仍按语言语义工作 | 修正类型和边界，记录必要实现依赖 |

## 自测

### 题目

1. 在 32 位 `int` 平台上，两个 `uint8_t` 操作数相加通常以什么类型执行？
2. `uint8_t result = 200 + 100;` 保存后的值是多少？
3. 为什么 `INT32_MAX + 1` 不能按 C 规则断言为 `INT32_MIN`？
4. `uint32_t value = UINT32_MAX; value += 1U;` 的结果是什么？
5. 构造 bit 31 掩码时，为什么推荐 `UINT32_C(1) << 31`？
6. `uint_fast8_t` 可以直接用于 1-byte 网络字段吗？

### 答案

1. 两个操作数通常都提升为 `int`，加法以 `int` 执行。
2. 加法得到 `300`，转换到 `uint8_t` 后为 `300 modulo 256 = 44`。
3. 有符号算术结果不可表示时属于未定义行为，语言不保证补码回绕。
4. 无符号运算按 `2³²` 取模，结果为 `0`。
5. 它明确让左操作数采用适合 `uint32_t` 的无符号类型，避免有符号左移边界。
6. 不可以假设；它只保证至少 8 bit，并可能比 1 byte 更宽。线格式还需要显式序列化。
