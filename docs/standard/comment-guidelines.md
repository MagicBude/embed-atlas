# 教材级注释规范

## 1. 目的

EmbedAtlas 不只交付可以运行的代码，还要让学习者理解代码背后的嵌入式知识。关键算法、协议处理和硬件示例的注释应达到“教材级”：读者能够从注释理解设计理由、输入边界、公式来源和常见陷阱。

教材级注释不等于注释越多越好。逐行把语法翻译成中文会遮挡真正重要的信息，并且很容易与代码不同步。

## 2. 应当解释什么

优先解释代码本身无法完整表达的信息：

### 为什么

- 为什么使用这种算法、数据结构或寄存器配置。
- 为什么不能采用看似更简单的方式。
- 该选择在速度、内存、精度或兼容性上的权衡。

### 领域规则

- 协议字段含义、位序、字节序和校验范围。
- 公式中的每个变量、单位和有效范围。
- 时钟、分频、采样点、溢出和舍入规则。
- 芯片手册、标准或算法模型中的关键依据。

### 边界与陷阱

- 零值、最大值、空输入和非法字符。
- JavaScript 数值范围与 C 整数溢出的差异。
- `volatile`、中断并发、DMA 缓冲区和内存屏障等硬件语义。
- CRC 反射、初始值、最终异或等常被遗漏的参数。

### 示例

当公式或位操作不直观时，给出一个短小、可以手算验证的例子。示例应帮助理解，不复制整套测试数据。

## 3. 不应注释什么

以下注释通常没有价值：

```ts
// 将计数器加一
counter += 1;

// 返回结果
return result;
```

代码已经准确表达这些动作。除非“为什么只加一”或“为什么此处必须返回”存在领域原因，否则不需要注释。

也应避免：

- 记录 Git 历史，例如“2026 年某人修改了这里”。
- 用注释长期保留废弃代码。
- 对不确定事实写肯定语气。
- 复制整段数据手册而不注明来源。
- 使用“显然”“很简单”等会阻碍初学者提问的表达。

## 4. 注释层级

### 文件或模块说明

适用于完整算法或工具核心，说明：

- 模块解决的问题。
- 支持和不支持的范围。
- 采用的标准、公式或模型。
- 关键设计约束。

### 公共函数说明

说明：

- 参数含义、单位和范围。
- 返回值及其单位。
- 可能的错误。
- 有副作用时说明副作用。
- 必要时给出一个调用示例。

### 行内注释

只用于局部不直观的原因、位布局、硬件限制或性能权衡。行内注释应该靠近相关代码，并保持简短。

## 5. TypeScript 工具示例

不推荐：

```ts
// 计算总位数
const bits = 1 + dataBits + parityBits + stopBits;
```

推荐：

```ts
/**
 * 计算一个 UART 帧在线路上实际占用的位数。
 *
 * UART 空闲状态为高电平，每帧固定包含 1 个起始位；随后是数据位、
 * 可选校验位和停止位。因此常见的 8N1 格式不是 8 位，而是
 * 1 + 8 + 0 + 1 = 10 位。这个结果用于计算理论传输时间，不包含
 * 帧与帧之间由软件、FIFO 或流控造成的额外间隔。
 *
 * @param dataBits 数据位数量，常见值为 5～9。
 * @param hasParity 是否启用奇校验或偶校验；启用时占用 1 位。
 * @param stopBits 停止位数量，例如 1、1.5 或 2。
 * @returns 单个 UART 帧占用的总位数，单位为 bit。
 */
export function calculateUartFrameBits(
  dataBits: number,
  hasParity: boolean,
  stopBits: number,
): number {
  const startBits = 1;
  const parityBits = hasParity ? 1 : 0;

  return startBits + dataBits + parityBits + stopBits;
}
```

该注释解释了公式、8N1 的常见误区、适用边界和单位，而没有逐行翻译三条语句。

## 6. 嵌入式 C 示例

不推荐：

```c
// 等待标志位
while ((USART1->ISR & USART_ISR_TXE) == 0U) {
}
```

推荐：

```c
/*
 * TXE 置位表示发送数据寄存器可以接收下一个字节，并不表示最后一个
 * 停止位已经发送完成；需要等待整帧结束时应检查 TC。此处仅用于向
 * USART1->TDR 写入下一个字节。生产代码还应加入超时，避免外设时钟
 * 或配置异常时永久阻塞。
 */
while ((USART1->ISR & USART_ISR_TXE) == 0U) {
}
```

注释指出了 TXE 与 TC 的区别以及无限等待的风险，这些信息无法只通过 `while` 语句读出。

## 7. 公式注释模板

涉及计算时，建议按以下内容组织：

```text
用途：计算什么工程量。
公式：使用的公式或算法模型。
变量：每个变量的物理意义和单位。
范围：输入有效范围和不支持情况。
精度：内部精度、显示舍入和可能误差。
示例：一组能够独立核对的输入与结果。
来源：标准、数据手册章节或可信参考实现。
```

不要求所有信息都塞进一个注释块。较长的推导应放在知识文章中，代码注释链接到文章或来源。

## 8. TODO 与临时注释

使用明确格式：

```ts
// TODO(issue-id): 支持 1.5 个停止位后，补充对应的输入校验测试。
```

- TODO 必须描述可执行的后续动作。
- 能关联 Issue 时写入标识。
- 不使用只有作者本人理解的缩写。
- 修复完成后删除 TODO，不让它变成永久背景噪声。

## 9. 审阅检查表

- [ ] 注释解释了关键的“为什么”，而不是复述语法。
- [ ] 输入、输出和单位明确。
- [ ] 算法变体、字节序和边界条件明确。
- [ ] 初学者不会被未定义的缩写阻断。
- [ ] 注释与当前代码一致。
- [ ] 长篇原理已经放入文章，代码中只保留必要摘要。
- [ ] 引用内容注明来源，没有复制大段受版权保护文本。
