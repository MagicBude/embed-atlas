# 开发工作流

## 1. 选择任务

- 从 `docs/project/status.md` 的下一步或已确认 Issue 中选择任务。
- 一次只解决一个清楚的问题。
- 大型模块先完成需求规格或 ADR，再写实现。
- 如果任务会改变路线图或模块边界，先更新规划并获得确认。

## 2. 创建分支

建议格式：

```text
<type>/<short-description>
```

示例：

```text
docs/uart-frame-guide
feat/base-converter
fix/crc-reflection
chore/vitepress-setup
```

仓库所有者直接在主分支进行早期初始化时，也应保持变更小而可检查。

## 3. 开发顺序

### 知识文章

1. 复制知识文章模板。
2. 明确目标读者和文章范围。
3. 收集官方标准、厂商手册或可靠参考资料。
4. 编写原理、示例、错误与来源。
5. 检查术语、链接和示例代码。

### 在线工具

1. 使用工具需求模板写清输入、输出、单位和参考向量。
2. 编写与界面无关的纯计算函数。
3. 先写或同步编写单元测试。
4. 实现 Vue 交互界面。
5. 编写原理说明并连接知识文章。
6. 检查桌面、窄屏、键盘和错误状态。

## 4. 自检

提交审阅前确认：

- [ ] 变更符合当前阶段和架构。
- [ ] 没有无关文件或生成产物。
- [ ] 注释符合教材级规范，而不是逐行复述。
- [ ] 带单位的数据明确标注单位。
- [ ] 文档链接、标题和代码块正常。
- [ ] 工具覆盖正常、边界、非法和参考向量测试。
- [ ] 已运行当前项目规定的检查命令。
- [ ] 必要时更新状态、架构或变更记录。

## 5. 审阅重点

审阅顺序建议为：

1. 事实和计算是否正确。
2. 范围和模块边界是否合理。
3. 初学者是否能够理解。
4. 错误输入和边界是否处理。
5. 实现是否清楚、可测试、可维护。
6. 样式和命名是否统一。

## 6. 提交与交付

提交信息遵守 `docs/standard/git-commits.md`。AI 助手未经明确要求不得自行提交或推送。交付说明必须列出：

- 完成了什么。
- 影响了哪些模块。
- 执行了哪些验证。
- 还有哪些未完成或需要决定的问题。
