# ADR-0002：中文优先并为路径式多语言预留架构

- 状态：Accepted
- 日期：2026-08-23

## 背景

EmbedAtlas 的当前差异化价值是面向中文嵌入式工程师提供容易学习和查阅的知识与工具，因此简体中文必须优先做好。同时，嵌入式技术具有全球通用性，工具、图表和高质量文章未来可能服务英文及其他语言使用者，也可能吸引更多国际贡献者。

如果完全按单语言实现，未来加入英文时可能需要改动 URL、计算核心和组件状态；如果现在立即复制完整英文站点，则会出现大量空页面、低质量机器翻译和双倍维护成本。需要在“现在可交付”和“未来可扩展”之间建立清楚边界。

## 决定

### 1. 当前保持中文单语言发布

- 简体中文是默认语言和当前唯一完整语言。
- 现有中文 URL 保持在根路径，例如 `/tools/base-bit-converter`。
- Phase 1 不显示没有实际内容的语言切换按钮，也不建立空的英文导航。
- 专业术语仍按文档规范在首次出现时保留准确英文名称和缩写。

### 2. 未来使用路径前缀增加语言

启用英文后采用：

```text
/                         # 默认简体中文
/tools/base-bit-converter # 简体中文工具页
/en/                      # 英文首页
/en/tools/base-bit-converter
```

后续语言使用稳定的 BCP 47 风格标识作为首段路径，例如 `/ja/`；是否需要地区变体必须根据真实内容决定，不提前创建目录。

中文继续位于根路径，避免多语言上线时破坏已经公开的中文链接。不同语言的同一内容使用相同的英文 `kebab-case` 页面标识，使语言切换能够建立确定映射。

### 3. 算法、状态与翻译文本分离

- `site/lib/` 中的纯计算核心不得返回中文或英文完整句子。
- 核心逻辑返回稳定错误代码和结构化参数，例如 `OUT_OF_RANGE`、`bitWidth` 和 `maxUnsigned`。
- Vue 组件通过当前语言的消息表把错误代码转换为用户提示。
- 工具名称、字段标签、按钮、帮助文字和复制反馈属于界面翻译资源。
- 协议常量、数值、位模式和测试向量不因语言变化复制计算逻辑。

这一决定从第一个工具开始执行，避免以后为了翻译而重写算法 API。

### 4. 内容按页面翻译，不把正文拆成键值表

- 导航、通用组件和短界面文字使用类型安全的语言资源。
- 知识文章、学习路线和长篇工具说明按语言保存独立 Markdown 文件。
- 各语言页面通过稳定内容标识建立对应关系，并记录源语言和翻译状态。
- 不把整篇文章拆成大量 JSON 字符串，否则会破坏 Markdown 审阅、代码示例和贡献体验。
- 不自动发布未经人工技术审阅的机器翻译；机器翻译只能作为草稿辅助。

### 5. 语言能力通过统一注册表配置

未来启用多语言时，站点配置应从一个语言注册表生成以下能力：

- 语言代码、显示名称、路径前缀和文本方向。
- VitePress 导航、侧栏、搜索文字和主题界面文字。
- 工具字段、错误信息、复制反馈和隐私提示。
- `lang`、canonical、`hreflang` 等页面元数据。

组件不得到处使用 `if (locale === 'en')` 拼接分支。新增语言应主要增加资源和内容，而不是复制业务组件。

### 6. 达到内容门槛后才启用新语言

英文公开入口至少满足：

1. 有明确维护者或审阅流程。
2. 首页、导航、搜索、关于和贡献说明已经翻译。
3. 所有已经公开的在线工具及错误提示可完整使用。
4. 至少有一条完整学习路线，或 10 篇经过技术审阅的核心文章。
5. 语言切换、缺失翻译提示、搜索和窄屏布局已经验证。

其他语言沿用相同质量门槛。门槛用于避免用户进入只有导航、没有内容的“空语言站”。

### 7. 缺失翻译必须明确

- 语言切换只链接到真实存在的对应页面。
- 没有目标语言版本时，可以提供“查看中文原文”的明确入口，但不能静默把用户送入混合语言页面。
- 翻译落后于原文时显示状态，避免旧译文看起来与当前中文内容等价。

## 理由

- 保留中文根路径，保护早期分享链接和搜索收录。
- 路径式语言 URL 可以独立索引、分享和缓存，比查询参数更稳定。
- 纯计算核心与语言文本分离，可以让所有语言共享同一组测试和算法修复。
- Markdown 按页面翻译更适合技术文章、代码块、来源和 Git 审阅。
- 设定启用门槛可以让项目先把中文内容和工具做好，再承担真实的翻译维护成本。

## 影响

正面影响：

- 当前开发量几乎不增加，但关键 API 从第一天就不绑定中文。
- 英文和其他语言上线时不需要复制工具算法。
- 每种语言可以独立审阅、搜索和部署，同时共享稳定内容标识。
- 中文特色不会因为追求国际化而在早期被稀释。

需要承担：

- 界面层必须维护错误代码到文案的映射。
- 多语言上线后，每次内容更新都要跟踪翻译同步状态。
- VitePress 导航、搜索和 SEO 配置需要按语言生成并验证。
- 相同页面的各语言版本会增加构建时间和审阅工作量。

## 未采用方案

- 现在立即上线中英文双站：当前内容量不足，会产生空页面并分散 Phase 1 精力。
- 永久只支持中文：限制工具复用和国际贡献，不符合长期开放方向。
- 使用 `?lang=en` 查询参数：不利于稳定分享、静态生成、搜索索引和缓存。
- 浏览器自动翻译作为正式英文版：术语、协议和安全提示无法获得项目级质量保证。
- 把所有 Markdown 句子放进 JSON：翻译键管理复杂，降低技术内容的可读性和贡献体验。

## 复审条件

出现以下情况时重新评估：

- 英文内容达到本 ADR 的公开门槛。
- VitePress 的多语言能力无法满足独立搜索、侧栏或 SEO 要求。
- 社区形成稳定的其他语言维护团队。
- 中文根路径与部署平台产生无法解决的 locale 路由冲突。
- 内容规模需要引入专用翻译管理平台或自动同步工具。
